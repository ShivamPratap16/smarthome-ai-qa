# API, Web UI and Load testing

This part tests the assistant **from the outside**, the way real clients use it:
over HTTP (API tests, Postman), through a real browser (Playwright) and under many users at
once (Locust). Nothing here needs a Gemini key. Everything runs with `LLM_MODE=fake`.

## Quick start

```bash
# API: contract tests + fuzzing (starts its own server on a random port)
.venv/Scripts/python -m pytest tests/api -q

# Web UI: Playwright + Chromium (first time only: .venv/Scripts/python -m playwright install chromium)
.venv/Scripts/python -m pytest tests/web -q            # add --headed to watch the browser

# Load: 20 users for 30 s, report in reports/load/latest.json
.venv/Scripts/python load/run_load.py
.venv/Scripts/python load/run_load.py --users 50 --duration 60s

# Postman / Newman (needs a running server)
LLM_MODE=fake .venv/Scripts/python -m uvicorn assistant.api:app --port 8000
npx newman run postman/smarthome.postman_collection.json -e postman/smarthome.postman_environment.json
```

Each pytest run writes `reports/api/latest.json` or `reports/web/latest.json`. The load run writes
`reports/load/latest.json`. Use `QA_NO_REPORT=1` to skip writing reports. The quality gate
(`qa/gate.py`) reads these files.

## Key ideas (interview notes)

### 1. Contract testing
A **contract** is the promise an API makes to its clients: "POST /v1/chat with
`{session_id, message}` returns a JSON object with `text`, `tool_calls`, `refused`, ... and
returns 422 if the message is empty." A contract test checks that promise and nothing else. It
does not check whether the answer is clever. It checks the shape, the status codes and the
types, because those break mobile apps and frontends.

We check every response in two ways:
1. Against the **published OpenAPI schema** (`/openapi.json`, generated by FastAPI; it is the
   same document Swagger UI shows). If our code returns something its own docs don't allow, the test fails.
2. Against a **strict pydantic model** taken from SPEC.md (`extra="forbid"`, `strict=True`). A
   renamed or added field fails the test.

Running both checks found real gaps (see "Bugs found" below). The published schema for `/v1/chat`
is just "any object", so a Swagger-generated client would know nothing about `BotReply`.

### 2. Property-based fuzzing (Schemathesis)
Normal tests use examples I thought of. **Property-based testing** turns this around. I state a
*property* that must hold for **every** input, and a tool (Hypothesis, used inside Schemathesis)
generates hundreds of inputs to try to break it. Schemathesis reads the OpenAPI schema and
generates:
- **valid** requests: random unicode messages of 1 to 2000 chars, odd session ids, any device id
- **invalid** requests: wrong types, missing fields, strings that are too long

The properties we check for each response:
- `not_a_server_error`: never a 5xx crash
- `response_schema_conformance`: the body matches the docs
- `content_type_conformance`: the Content-Type matches the docs
- `negative_data_rejection`: bad input is rejected with a 4xx
- `positive_data_acceptance`: good input is accepted

When a test fails, Hypothesis **shrinks** the input to the smallest example that still breaks
it, so the bug report is short. Use `FUZZ_EXAMPLES=500` to fuzz harder.

### 3. Page Object Model (POM)
The UI tests never use raw selectors. `ChatPage` holds all the locators (by `data-testid`) and
the actions ("send a message", "reset chat", "card for Living room fan"). A test then reads like a
user story:

```python
reply = chat.send("set living room fan to speed 4")
expect(chat.device_card("Living room fan")).to_contain_text("speed 4")
```

If a designer changes the HTML, only `chat_page.py` changes, not every test. Playwright's
`expect(...)` **auto-waits** until the condition is true or a timeout passes, so the tests need no
`sleep()` and are not flaky.

The web tests also use **network interception** (`page.route`):
- They hold the `/v1/chat` request to check that the typing indicator shows and the Send button
  is disabled while waiting.
- They return a fake 503 to check that the user sees a friendly error message.

When a web test fails, a full-page screenshot is saved to `test-results/<test name>.png`.

### 4. p95 latency and load testing
Locust starts N simulated users (default 20). Each user waits 0.5 to 2 s between actions
("think time"), like a real person. It records how long every request took.

- **p50 (median)**: half of the requests were faster than this.
- **p95**: 95% of requests were faster than this. Only 1 in 20 was slower.
- **p99**: 1 in 100 was slower than this.

We use p95 and not the average because one very slow request barely moves the average, but a
user still feels it. p95 is "the slow experience that still happens often". A budget like
"p95 ≤ 3000 ms" lives in `qa/thresholds.yaml`, and the CI gate fails if the build goes over it.
We also report **RPS** (requests per second the service handled) and the **error rate** (failed
requests ÷ all requests; a chat reply that is not 200 or has empty text counts as a failure).

**Fake mode vs live mode:** with `LLM_MODE=fake` the "LLM" answers instantly, so the load test
measures **our own service overhead**: FastAPI, guardrails, BM25 retrieval, SQLite logging and
the thread pool. That is the part we own and can optimise. To measure **end to end, including
Gemini**, start the server in live mode and point the runner at it:

```bash
LLM_MODE=live .venv/Scripts/python -m uvicorn assistant.api:app --port 8000
.venv/Scripts/python load/run_load.py --host http://127.0.0.1:8000 --llm-mode live --users 2 --duration 20s
```

Keep users and duration tiny in live mode, because the free Gemini quota allows only a few calls
per minute. Expect p95 of a few seconds, and 429 errors once you exceed the quota. Replay mode
(`LLM_MODE=replay`) is no good for load testing: random questions miss the cassettes and give
503s.

## Results (fake mode, this machine)

| Suite | Result |
|---|---|
| API (`tests/api`) | 51 passed (45 tests + 6 fuzz cases: 5 endpoints + 1 parent) + 3 known bugs (strict xfail) |
| Web (`tests/web`) | 15 passed (Chromium, headless) |
| Postman / Newman | 12 requests, 32/32 assertions passed |
| Load (20 users, 30 s) | 445 requests, 15.3 RPS, 0% errors, p50 9 ms, p95 92 ms, p99 100 ms |

In the load run, chat requests (p95 ≈ 100 ms) are about 25× slower than device reads (p95 ≈ 4 ms),
even refusals that never call the LLM. Most of that time goes to retrieval plus a SQLite write and
commit per message, behind one global lock. That lock is the first place to look if fake-mode
latency grows.

## Bugs found (kept as `xfail(strict=True)` tests, not fixed here)

`strict=True` means: once someone fixes the bug, the test "unexpectedly passes" and the run
**fails**, which reminds them to remove the marker. In the report these appear as cases with
`category: "known_bug"`. They are counted in `metrics.known_bugs`, not in `pass_rate`.

1. **Whitespace-only message is accepted.** (`test_contract.py::test_chat_whitespace_only_message_is_rejected`)
   `{"message": "   "}` passes `min_length=1`, goes to retrieval and the LLM (a wasted paid call),
   and is logged as an empty turn. The web UI trims input, but API clients don't. Fix:
   strip the message in a pydantic validator, then require length ≥ 1.
2. **OpenAPI does not describe the chat reply.** (`test_inprocess.py::test_openapi_documents_bot_reply_fields`)
   The `/v1/chat` endpoint returns `dict` without a `response_model`, so Swagger shows a free-form
   object. Fix: add pydantic response models (`response_model=BotReplyOut`).
3. **Error responses are not documented.** (`test_inprocess.py::test_openapi_documents_error_responses`)
   503 `{"error": "llm_unavailable"}` and the 404 for an unknown device are not in the spec.
   That is also why the fuzz test excludes Schemathesis' `status_code_conformance` check. Fix:
   `responses={503: {...}, 404: {...}}` on the routes.
